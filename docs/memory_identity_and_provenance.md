# 记忆身份、来源与共享设计

**状态：** 来源、共享、场景分区、上下文窗口与活动生命周期已接入原生运行时，并完成本机回归
**更新：** 2026-09-30

本文保留身份、来源与共享的设计要求。具体版本化字段、接口、默认迁移行为和验证边界以
[来源运行时 Profile 1](memory_provenance_runtime.md)为准；实现已纳入版本追踪，不代表已发布正式版本。

已逐项核对的实际触发、参数、删除与提示词行为见
[当前记忆维护定义](memory_maintenance_current_behavior.zh-CN.md)。该文区分已实现路径与本设计扩展。

## 1. 设计决定

DMW、NSG 继续按 Space 存储和管理。助手是稳定的身份，提示词是可修改的行为配置。
记忆的来源、事实主体和适用范围独立于存储空间及当前读取者。

- 默认隔离，跨助手、跨功能、跨情境使用必须有宿主明确配置的共享策略；该策略可以持久化，
  无需用户每次注入都确认。同一 Space 内也需要执行记录级适用性判断。
- 来源和事实主体 MUST 保持明确绑定；读取者不能因读取而成为原始参与者或承诺主体。
- 读取绑定 MAY 配置；不能把整个 DMW 或 NSG 永久限制为只有一个助手可以使用。
- Space 授权、记录共享策略和内容适用性是独立条件；检索权重和相关性不能替代任一条件。

## 2. 稳定的用户空间与功能空间

用户通常长期使用同一个个人 Space。宿主 MAY 为聊天、日程等功能配置稳定的功能 Space，
用于各自的数据管理与访问边界；无需为了切换助手、修改提示词或新建对话而创建 Space。
这是宿主组织方式，Core 不固定功能清单，也不要求所有宿主使用同一种空间布局。
功能 Space、对话 Space 和个人 Space 的角色可以由同一个 UUID 承担，也可以分开。

功能产生记录，不等于功能就是事实主体，也不等于记录只能给该功能使用。
例如用户偏好可在宿主指定的权威位置维护，由其他获授权功能读取；功能专属执行状态则留在
功能空间。SHOULD 优先共享读取同一权威记录，避免每个功能默认复制一份后各自修改。
权威位置是显式写入路由策略，不由模型根据内容擅自选择或迁移。

现有每轮一个 `memory_write_space_id` 的边界继续成立。将一个事实发布为共享记录或迁移到
其他空间需要独立、可审计的操作；同时读取多个空间不产生多空间写权限。

## 3. 助手身份与提示词版本

默认助手提示词配置指 `assistant` Prompt Space 的系统提示词设置，不要求在对话中途修改
角色卡。下面的身份稳定规则同时覆盖独立的角色资源编辑，但这两个配置入口不是同一功能。

宿主 MUST 为默认助手和用户创建的助手保留稳定身份。当前原生响应会话使用已有
`character_id` 表示所选角色资源；默认助手也需要显式身份映射，不能因为没有个性化角色
文本就把来源当成“任意助手”。本设计不新增第二套与 `character_id` 重复的公开 UUID。
身份与角色资源的具体宿主映射需在实现时明确，并覆盖默认助手路径。

- 修改同一助手的提示词、角色卡正文、显示名、模型或恢复默认提示词，MUST NOT 自动改变
  其身份、清空记忆、转移经历或扩大共享权限。
- 提示词内容哈希或 revision 只表示当时的配置版本，不能充当助手身份。
- “默认助手”是宿主的选择位置。把默认选择从 A 改为 B 是选择了另一个身份；A 的经历
  不自动变成 B 的经历。
- 创建或复制为一个新助手需要新身份；内容相同不构成身份相同。若用户要把大幅改写后的
  人设作为全新身份，应使用显式新建/切换操作，而不是由模型猜测提示词变化的含义。
- 切换会话角色只影响之后的活动身份。历史消息与记忆的来源 MUST 保留事件发生时的身份，
  不能事后使用会话的当前 `character_id` 回填所有历史。

当前 `assistant` Prompt Space 是进程级具名提示词槽位，不是用户 Space、功能 Space 或
某个助手的身份。覆盖它影响所有走该回退路径的请求，不提供每用户助手身份隔离。
当前新会话使用显式 `character_id` 或宿主为个人 Space 设置的默认角色映射；两条路径都有稳定角色身份。

## 4. 记录与证据的逻辑模型

下表是所需语义，不是可直接提交的 JSON、Frontmatter 或 `.nsg` schema。

| 维度 | 需要保留的信息 | 不得据此推断 |
| --- | --- | --- |
| 当前存储归属 | 当前 Space、模块、记录 ID、记录版本 | 原始产生位置或经历者 |
| 原始证据 | 原始 Space、功能来源（如有）、对话和消息引用、发生时助手/角色身份、说话者、证据类型 | 当前读取者亲历、说话内容必然为真 |
| 配置追踪 | 证据产生时可获取的提示词/角色配置 revision | 助手身份变化 |
| 事实语义 | 主体、参与者、承诺责任人，以及陈述/推断/修正等状态 | 记录作者就是事实主体 |
| 适用范围 | 用户、关系双方、对话、世界/时间线、有效时间等必要约束 | 同一用户或同一 Space 内全部通用 |
| 共享策略 | 获准使用的助手、功能或情境，以及策略版本 | 读取权等于写入权、规则权威或承诺继承 |

证据可以来自对话，也可以来自用户编辑、工具结果或导入资料。后几种不能伪造对话或消息 ID。
运行时 MUST 从可信调用与已存事件中捕获来源；模型可以提出事实解释和适用性候选，但不能
自行签发来源、身份或访问权限。来源可验证表示出处可追踪，不表示其陈述已证实。

记录 SHOULD 引用稳定证据标识，避免在每条记录中重复完整对话元数据。证据存储应属于既有
记忆/审计与可移植数据设计，不另建一套竞争性的事实库；具体存储与 schema 另行版本化。
跨空间记录引用 MUST 至少区分 Space、模块和局部记录 ID；不能仅按裸 `id` 去重或覆盖。

### 4.1 原始证据、提案、调度与批准

来源不能只枚举成“用户 / MO State / NSG”三个互斥值。一条规则可以由用户提供证据、
由自动治理器提出修正、由 MO State 运行时协调处理，再由用户批准；这些信息需要同时保留。
每次创建、修正、合并、导入及批准应形成可追踪的修订事件，而不是覆盖记录上的单个来源标签。

| 维度 | 目标语义 |
| --- | --- |
| 原始证据与原作者 | 用户陈述、手工规则、工具结果、导入资料或已有记录；保留实际出处及可验证程度 |
| 提案者/派生组件 | 用户直接编辑、DMW Distiller、NSG Governor 等；模型生成与用户直接撰写分开 |
| 触发与协调 | 用户手工触发、达到自动批次阈值、MO State 恢复/协调、导入；不因此改变事实作者 |
| 执行与变换 | Core 验证与提交的操作/批次、派生父记录版本、目标记录修订；区分执行者与提案者 |
| 批准与权威 | 显式作者批准或宿主策略授权、相应操作与策略版本；Canon/Draft 是状态，不代替批准证据 |
| 运行配置 | 实际使用的提炼/治理提示词 revision、适用参数与策略版本；不能只记录前台助手提示词 |

例如：“用户编写规则 R → Governor 提出修订 C → 用户批准 C → R 的新版本”必须保留
原作者、候选证据与模型提案关系，同时追加批准事件。批准不意味着候选正文最初由用户撰写。
用户点击立即提炼也只表示人工触发，提炼结果仍是模型提案。

MO State 的确定性投影属于派生状态，不能当成独立事实证据，再被提炼回去形成自我佐证。
若后续运行时确实提出规则变更，应记录协调者与提案组件，并回链原始 DMW/NSG/消息证据；
“由 MO State 得出”不能替代证据链。治理器对旧节点的修正也必须保留父版本和修正理由。
运行时可自动提交的变更记录策略授权；需要 Canon 批准的变更保留既有作者边界。

上述身份、触发和操作关联由可信宿主/运行时捕获。模型生成的 `source_evidence` 文本只能作为
候选说明，经校验后才能关联真实证据；不得把模型填写的“用户批准”当作批准事件。
当前逐修订来源文件把上述批次、提案与批准关系关联起来；字段和非对话来源的未知边界见运行时 Profile。

## 5. DMW 与 NSG 的不同适用方式

### DMW

用户偏好可以共享，但必须保持相同用户主体，并区分现实偏好与故事中的角色偏好。
经历、关系和承诺绑定实际参与者与责任人。助手 B 获准知道用户与 A 的经历，并不意味着
B 参与过该事件或继承 A 的承诺。关系状态不能仅因为用户相同就投射给另一助手。

事实纠正产生修订并链接原始证据。合并和再次蒸馏 MUST 保留支持证据的来源集合；不能把
“本次读到旧记忆”计作一次独立新证据，或把共享来的经历改写成当前助手的亲历。
同主题但主体、世界或时间不同的事实不能自动合并；冲突证据应保留修正/争议关系。

### NSG

规则绑定其适用的世界、规则集或情境；角色专属规则还需要角色范围。
`graph_id` 可以组织图，但相同字符串（特别是默认值）不能证明不同空间属于同一世界。
世界/时间线的稳定映射需宿主明确指定，不能由名称、提示词相似度或检索分数推断。

Canon 权威限定在其原本适用范围。跨空间读到 Canon，不会使它自动成为目标世界的 Canon。
在另一情境采用规则需要显式适用映射和既有 Canon 治理；共享策略不能绕过 Draft 隔离、
Revision Candidate 或作者批准边界。

## 6. 注入与 MO State

目标处理顺序为：宿主授权空间 → 检索候选 → 校验记录共享策略与适用性 → 构造带来源的
合格输入 → MO State 投影及模型上下文组装。状态投影和正文注入 MUST 使用同一合格输入集；
不能只在最终文本中过滤，却让不适用的关系或规则先改变状态。

模型上下文至少应表达：可区分的记录引用、证据出处、主体/参与者、与当前助手的关系
（自身经历、外部经历、共享偏好/知识或来源未知），以及影响使用的适用限制。
空间显示标签只是可读名称，不能替代稳定标识和证据链。来源说明属于证据元数据，不授予
正文系统指令权威；来源展示还须遵守授权，不能因共享事实而泄露未授权原始对话。
身份和适用限制应与相应正文一起保留或一起移除，不能在预算裁剪时只留下无归属的事实。

当前场景、关系姿态和承诺激活必须匹配当前主体与情境。同一助手的平行对话也不必然共享
一个当前场景；只有宿主显式声明属于同一连续情境时才能沿用。Space 仍是写入一致性边界，
但不应被直接等同为唯一叙事情境。当前按个人 Space/角色/连续情境分区，默认连续情境为会话 ID。
快照与缓存还需覆盖当前身份、情境和共享策略版本，避免身份/策略改变后复用不合格状态。

例如 B 可使用“不喝咖啡”的共享偏好；需要说明出处时可说“你曾在与 A 的对话中提到”，
不能说“你上次告诉过我”。产品不必在每次回复中重复来源，运行时与模型仍需能区分来源。

## 7. 导入、历史记录与证据生命周期

- 共享读取默认不复制数据。显式复制、导入或迁移保留原始来源，另记当前位置与派生关系。
- MOC `space_map` 表示目标存储映射，不是历史重写；证据原始 Space 与导入后可解析的本地
  引用需分别保留。不能一律重写所有来源标识，也不能因此继承目标空间的共享授权。
- 原始证据未随导入提供时，保留外部/未解析引用并标明可验证程度；不得伪称已验证。
- 旧记录缺来源时标记未知，不能根据当前助手、当前空间、角色关联或相似正文补造来源。
  缺失字段不表示全局共享。原有本地使用路径可保留，新的跨助手使用必须先有明确映射与策略；
  主体不明的关系/经历和范围不明的规则不能进入目标状态投影。
- 原消息删除、证据失效或访问撤销时，不能继续声称有可访问的证据。证据摘要、引用或墓碑
  的保留遵守既有删除与授权策略；不因追踪来源而强制无限保留原始对话。删除对话与删除派生
  记忆仍是独立控制动作，需明确记录证据是否仍可用。

当前 `delete_conversation` 保留已提炼记忆，独立控制接口负责停止来源提炼与撤销证据；原消息
删除后标为不可活动读取。删除快照仍可能保留原文，不声称所有副本已擦除。
扩展应明确区分“删除聊天”“停止该来源后续提炼”“撤销其派生事实”，默认删除聊天不等于
后两项；撤销需要考虑同一事实是否还有其他独立证据，不能直接把整个共享 Space 清空。

### 8.1 参数控制的扩展边界

2026-09-30 已实现：[MO State 活动生命周期 Profile](memory_lifecycle_runtime.md)。
`mo_state.memory_lifecycle` 支持 `enabled`、`decay_after_turns`（默认 48）、
`forget_after_turns`（默认 240）、`decay_factor`（默认 0.9）、`auto_forget`。
轮数范围 1–1,000,000，倍率严格介于 0 和 1；设置是实例级进程资源，由宿主同步，尚无
每 Space 覆写。12 轮 DMW/NSG 模型提炼配置保持独立，仍为 1–200。

自治档在有显式 DMW 写权限的成功文本响应完成时，原子记录生命周期事件及当时身份/配置，
然后按 Space/对话/助手推进活动计数。失败响应、重放、闲置和单纯检索不增加计数。
未知旧记录仅通过匹配的会话绑定或实质命中登记；旧日历时间不折算成累计轮次。
共享记录需要每个已登记情境都满足间隔，其他故事不能独自消耗这里的保留期。

默认只淡化非核心 event；关系、角色、世界、current、重要度至少 0.8 的事件、关系/显式
正文引用、场景/开放线程引用，以及承诺/待办标签受保护。未标记承诺的正文语义不由此算法
自动推断。归档后满足低重要度/低权重及额外未命中轮数，才允许物理遗忘；可独立关闭。
内容修订会保守重置已登记时钟，单纯注入不刷新实质命中。

轮次、文件、索引、墓碑和审计通过持久预备提交恢复，重启不重复老化。已接受事件使用冻结
配置，配置变化作用于新事件；设置操作本身不删除记录。原生自动及 HTTP 维护路径不再走
180 天的旧日历算法，低层显式 Rust 兼容接口仍保留该算法。
故事内时间和容量回收仍是独立产品问题；来源链由 Profile 1 单独实现。

自动提炼继续使用非重叠的未处理证据批次；上下文窗口独立运行。默认累计 12 个完整问答后
移出最旧 2 轮，之后每新增 2 轮再移出 2 轮；不删除持久消息，不丢弃未确认的提炼证据。
`history_window` 可关闭或修改窗口参数，token 预算仍为最终硬限制。MO State 逐响应投影
不受维护批次阈值限制。

## 9. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 默认助手修改或恢复提示词 | 身份与记忆归属不变，后续证据可区分配置版本 |
| 默认选择由 A 改成 B，或复制 A 为新助手 | 身份不同，不继承 A 的经历与承诺 |
| A、B 在同一个用户/功能 Space | 不能因空间相同跳过共享与适用性校验 |
