# MORP 0.2 设计与归因协议

MORP 的全名是 **MOMO Role-playing**。它既可评估 MOMO，也可通过适配器评估其他记忆系统和角色扮演框架。0.2 的目标不是产生一个容易满分的总榜，而是回答：失败发生在模型、记忆写入、检索、MO State 投影，还是最终生成。

## 为什么不能只比较“完整上下文”和“MOMO 全开”

这两个结果只能说明两条完整路径不同，不能定位差异来源。完整上下文同时给模型更多原文；MOMO 全开同时改变 DMW、NSG、MO State、提示长度和维护等待。若再换候选模型，模型能力与系统能力会完全混在一起。

0.2 固定同一个候选模型、部署 revision、温度、输出预算、事件流和重复次数，运行以下七个 MOMO 臂：

| 臂 | DMW | NSG | MO State | 主要问题 |
|---|---:|---:|---:|---|
| `basic_context` | 关 | 关 | 关 | 当前 conversation 的模型基线 |
| `dmw_only` | 开 | 关 | 关 | DMW 的净作用 |
| `nsg_only` | 关 | 开 | 关 | NSG 的净作用 |
| `dmw_state` | 开 | 关 | 开 | MO State 如何使用 DMW |
| `nsg_state` | 关 | 开 | 开 | MO State 如何使用 NSG |
| `dmw_nsg` | 开 | 开 | 关 | 两类记忆组合，不经过状态投影 |
| `all_enabled` | 开 | 开 | 开 | 完整产品路径 |

`scenario-plan --matrix causal` 生成这七个臂，并显式保存臂顺序。运行顺序按 case/repeat 轮换，避免服务预热、限流和时间漂移总是偏向同一臂。

日常先用 `--matrix core` 的三臂 `basic_context`、`dmw_nsg`、`all_enabled`。前一差值回答组合记忆是否有增益，后一差值回答 MO State 在相同组合记忆之上是增益还是伤害。只有三臂发现回归，再运行七臂 `causal` 定位 DMW 或 NSG。`paired` 保留为最小的完整路径烟雾测试。

另设一次性 `full-context-replay` 和可选的 oracle 检索作为模型上限控制。它们不进入 MOMO 主分：

- 同模型跨臂比较，估计 MOMO 组件的增量影响；
- 同一臂跨模型比较，估计模型敏感性；
- `full-context-replay` 高而 MOMO 低，优先查系统管线；
- 两者都低，优先查题目有效性、提示和模型能力；
- 实际检索已命中但回答错误，优先查读入、MO State 或生成；
- 实际检索未命中，不能把错误记到最终生成模型头上。

## 六层评分，不合并成一个万能分数

| 层 | 输入与观测 | 指标 |
|---|---|---|
| L0 题目有效性 | 双人标注、反事实对、争议样本 | 标注一致率、歧义率、题目泄漏率 |
| L1 模型上限 | 允许读取的完整原文或 oracle 证据 | 客观字段、角色盲审、拒答准确率 |
| L2 写入/提取 | 原始事件与 DMW/NSG 产物 | 事实保真、更新/撤销、来源、隐私污染 |
| L3 实际检索 | 查询与返回 ID/Space/顺序 | support recall、precision、nDCG、空召回率 |
| L4 MO State | 检索输入与确定性投影 | 投影事实准确率、冲突、越权、降级抑制 |
| L5 最终角色回复 | 回答、客观字段、证据、盲审 | 事实、人格、情绪轨迹、行动权、泄漏、延迟、成本 |

主报告应同时给出各层结果和失败路径。`MOMO lift = 某组件臂 - basic_context` 只在配对完成时计算。没有人工校准时，模型裁判结果标为 provisional；缺失、超时和裁判分歧不会被隐藏在平均分中。

## 0.2 角色扮演集

`benchmarks/morp/roleplay_v02.py` 首批提供 6 个机制族、每族 2 个相反结局、2 种依赖，共 24 个 case。每段 24 个历史事件，跨越第 12/24 条维护边界：

1. 逐步重建信任：有限授权不能被写成完全和解；
2. 公开场合的隐私与同意：公开范围变化不能泄露私聊内容；
3. 悲伤后的有限恢复：情绪会演化，能力和承诺仍有边界；
4. 证人和来源可靠性：直接见证与无法确认必须得到相反答案；
5. 压力下的用户行动权：授权有范围，沉默和过去行为不是同意；
6. 受伤后的场景连续性：身体限制会更新，但角色能力不能被抹掉。

每个反事实对的历史、问题和 schema 完全相同，只有最后一个决定性事件不同。两条分支必须给出不同客观字段，因此“始终同意”“始终拒绝”“始终不知道”最多通过一半。所有角色和文本均为原创成年人，并使用匿名角色机制，避免知名角色名触发训练记忆。候选模型看不到答案、rubric、禁止词、组件臂和依赖标签。

角色题必须同时保留：

- `facts_only_diagnostic`：检查事件状态、授权、位置和限制；
- 两个独立盲审或一名可审计人工裁决：检查人格机制、情绪连续性、自然表达和行动权；
- 实际检索诊断：只记录返回 ID、来源 Space 和 token 估算，不把记忆正文复制到公开审计；
- 隐私禁止词检测：泄漏直接判为违规，缺失回答不能算作隐私通过。

首批 24 条是开发集，不是足够发布榜单的规模。0.2 后续要加入中文等价版本、人写自然对话、会根据角色回复改变的动态分支、多方会话、工具结果、跨周时间、冲突记忆和故障注入，并将一部分最终测试保持隐藏。

## MO State 的放大风险与处理

MO State 位于检索和最终生成之间；它的错误会影响回复，回复又可能进入下一轮提取，因此需要单独的隔离与审计。

当前实现增加以下约束：

- `injection_mode = "shadow"`：照常观察、投影、持久化和记录审计，但不把状态上下文注入回复；
- 投影编译报错或检索降级时禁止注入，避免失败输入继续进入生成；
- 审计保存本次真实检索输入的 SHA-256、DMW/NSG 数量及来源 Space，明确其范围是 `retrieved_subset`；
- 回复审计列出实际检索 ID、类型、Space 和估算 token，不泄露正文；
- 前台生成与 DMW/NSG 维护使用不同的每 Space 名额，避免长维护独占本地前台许可。

正式启用前先以 shadow 运行同一批对话，比较“投影是否正确”和“不注入时回答如何”。只有 L3 检索、L4 投影、故障抑制都达标后，才将该配置切到 active。新版本或新模型仍应重新 shadow，而不是把历史通过当作永久授权。

## 延迟与成本口径

前台完成时间、首字时间、维护屏障、嵌入、DMW、NSG、MO State 和裁判调用分别统计。测试为了确定性而强制 `maintenance/drain` 的整段等待不等同于普通聊天单条延迟，但它代表“新会话必须立即读到刚写事实”时的同步成本。

默认 `history_mode = "recorded"`：固定用户/助手转录直接写入 conversation 和维护队列，候选模型只回答最终探针。它隔离记忆系统贡献，也把 24 条历史的一个 case 从 25 次候选生成降为 1 次。`history_mode = "live"` 才让候选逐轮回复，用于小规模检查“状态→回复→再次提取”的反馈循环；live 分数和 recorded 分数必须分开报告。

发布报告至少给出 p50/p95/p99、超时率、并发数、输入/输出 token 和后台供应商账单。缺失后台 usage 时总成本保持 unknown，不能只用前台 token 声称 MOMO 更便宜。

## 研究依据

- [LongMemEval](https://arxiv.org/abs/2410.10813) 将长期记忆分成提取、多会话推理、时间推理、知识更新和拒答，并区分索引、检索和读取设计。
- [MemoryAgentBench](https://arxiv.org/abs/2507.05257) 补充准确检索、测试时学习、长程理解和选择性遗忘。
- [LoCoMo](https://arxiv.org/abs/2402.17753) 使用长达多会话的人工修订对话与时间事件图，说明短事实列表不足以代表长期互动。
- [RMTBench](https://aclanthology.org/2025.findings-emnlp.730/) 强调多轮、用户意图导向的角色扮演，而非孤立角色问答。
- [PersonaGym](https://aclanthology.org/2025.findings-emnlp.368/) 采用动态情境和人类对齐评分，并表明更大模型不必然有更高 persona 能力。
- [Anonymous Benchmarking](https://aclanthology.org/2026.sigdial-1.15/) 发现知名角色名会提供隐含训练记忆线索，因此 MORP 主集使用原创匿名角色。
- [Memory-Driven Role-Playing / MRBench](https://aclanthology.org/2026.findings-acl.1175/) 将记忆驱动角色扮演分成 Anchoring、Selecting、Bounding、Enacting，支持分阶段诊断。
- [ARES](https://aclanthology.org/2024.naacl-long.20/) 与 [MIRAGE](https://aclanthology.org/2025.findings-naacl.157/) 支持将上下文相关性、忠实度、回答质量和 RAG 组件分别评估。

这些工作提供维度和方法参考；MORP 不复制其受版权或原许可约束的数据。

## 开源与版本安排

0.2 阶段建议保留在 MOMO 仓库内的 `benchmarks/morp`，但保持独立版本、CLI、数据 manifest、适配器接口和许可证说明。这样可以随着 MOMO API 变化同步修正，外部记忆系统仍能通过 `full-context` 或自己的 runner 使用。

当数据 schema、检索 trace 接口和评分协议稳定，并出现两个以上独立外部适配器或维护者后，再拆成单独仓库和发布包。现在立即拆仓只会增加双边版本漂移；永远内置又会让它看起来只是 MOMO 的自测。先同仓独立版本，是当前较稳妥的边界。

## 1.0 发布门槛

MOMO 1.0 不以“某次总分接近满分”为条件，而以以下证据同时成立为条件：

- L0 人工复核不存在高比例歧义，反事实对不能被固定策略通过；
- 至少两个候选模型下，MOMO 组件增量方向稳定，且失败能定位到具体层；
- 隐私、撤销、未知、用户行动权和故障抑制没有严重回归；
- MO State shadow 与 active 差异经过审查，投影错误不会被注入；
- 真实目标部署的前台 p95、超时率和总成本达到预先登记的业务线；
- 进程重启、维护超时、非法补丁和部分写入的恢复测试通过；
- 角色回复经独立人工抽检，不只依赖与候选同源的模型裁判。

在这些条件完成前，适合发布 1.0 release candidate 或 preview，不适合宣称生产级 1.0.0。
